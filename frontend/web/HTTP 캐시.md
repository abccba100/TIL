## 1. HTTP 캐시


### 1.1 기본 개념

HTTP 캐시는 이름에서 부터 알 수 있는 듯이 서버에 한 번 요청했던 리소스(이미지, 자바스크립트 파일, JSON 데이터 등)을 캐싱(저장) 해뒀다가 다음에 같은 요청이 들어왔을 때 서버에 한 번 더 요청을 보내는 것이 아닌, 캐싱 되어 있는 리소스를 사용하는 것이다.

- 여기서 “tanstack-query 에서 제공하는 데이터 캐싱 기능이랑 매우 유사한 것 같은데 어떤 차이일까?” 라는 궁금증이 들어서 찾아봤다
    
    간단하게 정리하자면,  
    tanstack-query에서 제공하는 캐시는 JS 런타임 안에 있다. 즉 브라우저를 새로고침하면 날아가버린다. 또한 서버는 캐싱 정책(언제까지 fresh 상태로 볼지 등)을 모르며 단순히 프론트엔드 코드에 의해 결정된다.  
    HTTP 캐시는 브라우저 레벨에서 이루어지기 때문에 새로고침을 해도 날아가지 않으면 캐싱 정책을 서버에서 결정하여 응답 헤더로 내려준다.  
    최종적으로 두 캐시는 목적이 다르다. HTTP 캐시는 네트워크 비용 절감을 목적으로 하고 tanstack-query의 캐시는 자동 최신화, 낙관적 업데이트 등 HTTP 캐시에서는 해줄 수 없는 일들을 주목적으로 한다.  
    

### 1.2 HTTP 캐시 종류

HTTP 캐시는 크게 로컬(브라우저) 캐시와 공유(프록시) 캐시로 나뉜다.  
간단하게만 먼저 설명하면 로컬 캐시는 개인을 위한 캐시, 공유 캐시는 다수를 위한 캐시이다.  

1. **로컬 캐시**
    
    로컬 캐시하면 대표적으로 브라우저 캐시를 말하는데, 위에서 말했던 개념과 같이 서버에서 받은 리소스를 캐싱하고 같은 요청이 들어오면 캐싱된 리소스를 준다.
    
    !image.png
    
2. **공유 캐시**
    
    공유 캐시하면 대표적으로 프록시 캐시를 말하는데, 로컬 캐시와 차이점을 캐싱을 로컬에 하지 않고 프록시 서버에 해둔 뒤에 다른 사용자들도 같은 요청을 하면 프록시 서버에서 캐싱된 리소스를 준다.
    
    !image.png
    

- 여기서 “그러면 많은 사용자들에게 캐싱된 리소스를 제공할 수 있으니까 공유 캐시가 로컬 캐시보다 압도적으로 좋은 거 아닐까?” 라는 생각이 들어서 찾아봤다
    
    일단 이것부터 먼저 생각해야 하는데 로컬 캐시를 이용하면 네트워크 요청이 나가지 않고 로컬에 있는 리소스를 이용하고 공유 캐시는 프록시 서버까지는 요청이 가야하기 때문에 네트워크 요청이 발생한다.  
    때문에 내가 생각했던 것과는 반대로 오히려 공유 캐시가 성능 감소 및 비용 증가로 이어질 수 있게 된다  
    하지만, 사이트에 처음 방문하는 사용자, 캐시를 지운 사용자, 시크릿 모드 사용자와 같이 로컬 캐시가 자체가 없는 경우에는 공유 캐시가 매우 유용해지게 된다.  
    이걸 알고 나니 이어서 “그러면 로컬 캐시가 없을 땐 공유 캐시를 이용하고 이후 부턴 로컬 캐시를 이용하면 되지 않을까?” 라고 생각했는데 이미 기본 동작이 이렇다고 한다.  
    

### 1.3 사용 방법

1. **Cache-Control**
    - **Cache-Control: no-store :** 리소스를 캐시 하지 않음
    - **Cache-Control: max-age=3600 :** 캐시 유효기간을 설정(초 단위)
    - **Cache-Control: private :** 프록시 캐싱 비활성화
    
    여기서 놀라운 점이 Cache-control을 따로 설정 안해주면 자동으로 들어가는 기본 값이 있을 줄 알았는데 경우에 따라서 상황이 달라진다.  
    `Last-Modified` 가 있는 경우에는 브라우저가 공식을 이용해서 알아서 대충 캐싱을 해버리고  
    `Last-Modified` 와 `ETag` 가 둘 다 없을 땐, 캐싱 없이 매번 새로운 요청을 날린다.  
    
2. **Expires**
    - **Expires: Wed, 30 Jan 2024 00:00:00 GMT :**  2024년 1월 30일 자정까지 캐시 유효
    
    **Cache-Control: max-age**랑 역할이 겹치는 것 같은데 그게 맞다 그래서 두 개가 같이 쓰이게 되면 Expires는 무시되고 max-age의 값으로 설정된다.  
    이유는 max-age는 초 단위 관리가 가능해서 훨씬 유연하기 때문이다.
    
3. **Last-Modified** 
    - **Last-Modified: MON, 1 Jan 2024 00:00:00 GMT :**  2024년 1월 1일 자정에 리소스가 변경됨
    
    쉽게 설명하자면, 캐시가 만료되고 서버한테 “이 날짜 이후로 이 데이터 바뀐 적 있어?” 라고 물어볼 때  
    서버한테 줄 날짜가 필요하기 때문에 클라이언트 기준 마지막에 리소스 변경 날짜를 나타내는 것이다.
    
4. **ETag**
    - **ETag: "abc123"**  리소스 고유 문자열 : "abc123"
    
    쉽게 설명하자면, 리소스 내용을 기반으로 고유한 문자열을 만들고 이걸 서버한테 주면서 “리소스 내용 바뀐 거 있어?” 라고 물어볼 때 쓰기 위해서인데 매번 내용을 다 보내면 용령이 부담되니까 문자열 형태로 만들어서 사용한다.
