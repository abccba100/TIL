## 1. Web Worker


### 1.1 기본 개념

Web Worker는 싱글 스레드로 동작하는 JS에서 무거운 연산을 진행할 경우 UI가 멈춰버리는 문제 등을 해결하기 위한 기술로 메인 스레드와 분리된 백그라운드 스레드에서 작업을 진행할 수 있도록 해준다.

- 이벤트 루프와 헷갈리기 쉬운 부분
    
    JS는 이벤트 루프 기반이니 멀티 스레드와 다른 게 없다고 생각할 수도 있지만,  
    이벤트 루프를 통해서 가져온 이점은 fetch, setTimeout처럼 시간을 기다려야 하는 작업을 스레드에서 진행하지 않고 Web API라는 공간으로 뺀 것이지 연산 자체를 멀티 스레드처럼 진행할 수 있는 것은 아니다.  
    정리하면 이벤트 루프를 통해서 비동기를 구현할 수는 있지만, 멀티 스레드 자체의 기능을 구현한 것은 아니다.  
    

### 1.2 왜 필요할까?

지금까지는 많은 데이터, 연산 등을 다룰만한 프로젝트를 해본 적이 없어서 처음 이 기술을 보고  
”굳이 왜?” 라는 생각을 했는데 몇만 건 단위의 연산을 진행하게 된다면 몇초 동안은 해당 작업만 진행하게 되니 spinner 멈춤 뿐만 아니라 사용자의 클릭 같은 이벤트들도 처리하지 못하는 매우 큰 UX 하락으로 이어질 수 있는 문제가 생긴다.

- 여기서 “그러면 무조건 도입하는 게 좋을까?” 라는 생각을 해서 찾아봤다
    
    “작은 연산이라도 Web Worker한테 맡기고 메인 스레드는 계속 이벤트를 처리하면 UX가 조금이라도 더 향상될 수 있지 않을까?” 라고 생각하면서 도입하면 안된다.  
    우선, Web Worker 생성 및 메모리 비용이 발생하고, 메인 스레드와 Web Worker는 메모리를 공유하지 않기 때문에 스레드 끼리 데이터를 주고 받을 떄 직렬화/역직렬화가 발생하는데 가벼운 연산을 위해서 위와 같은 동작을 하기에는 배보다 배꼽이 커지는 것과 다를 게 없다.
    

### 1.3 언제 사용하면 좋을까?

1. **무거운 연산을 하는 경우**
위에서 말했던 것처럼 무거운 연산을 하는 작업을 할 때 무거운 연산을 Web Worker한테 맡기면 메인 스레드는 spinner를 계속 움직이거나 유저의 클릭과 같은 이벤트를 처리하는 등 UI가 멈춰버리는 현상을 막을 수 있다.
2. **백그라운드에서 작업이 돌아가야 하는 경우**
    
    예를 들어서 1.5초 마다 돌아야하는 작업이 있어서 구현을 해뒀는데 브라우저 정책으로 인해 쓰로틀링에 걸리게 되면 작업이 무시되어 버려서 문제가 생긴다.  
    이 문제를 해결하기 위해서 백그라운드에서 동작하는 Web Worker에게 작업을 맡기면 쓰로틀링에 걸리지 않고 계속해서 작업을 이어 나가게 된다.
    
    - 쓰로틀링이란?
        
        쉽게 설명하자면 브라우저가 판단했을 때 비활성화 된 탭에서 반복적으로 이벤트가 발생하면 이벤트를 지연하거나 제한해버리는 것이다.



---
Web Worker 공부해보고 가장 아쉬웠던 게 지금 하고 있는 프로젝트 중에서 Web Worker를 적용할 만한 프로젝트가 없다는 것이다.  
직접 프로젝트에 적용 해보면 성능 향상도 크게 되고 재밌을 것 같은데 정작 Web Worker를 쓸 정도로 큰 규모의 데이터를 다루거나 백그라운드에서 지속적으로 작업 할 일이 없다보니 너무 아쉽다.  
그래서 기회가 된다면 꼭 큰 규모의 데이터를 처리하는 프로젝트를 한 번 해보고 싶다.  
정보가 많아서 렌더링 할 것도 많다면 어떻게 렌더링을 효율적으로 할 건지, 어떤 연산까지 Web Worker에게 맡기고 어디까지 메인 스레드에서 관리 할 건지 등 고민할 거리가 되게 많은 것 같다.
